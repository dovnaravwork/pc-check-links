# PC Check Field Guide — GitHub Pages release

Эта папка — **источник истины (source of truth)** для опубликованной статической версии:

- `index.html` — структура, инструкции и мастер проверки;
- `style.css` — адаптивные, интерактивные и печатные стили;
- `script.js` — локальные статусы, заметки, verdict, копирование и печать;
- `commands.js` — локально формирует проверяемые команды WinGet и автосбора Windows;
- `tests/site.test.mjs` — dependency-free контракты релиза;
- `.github/workflows/verify.yml` — проверка тех же контрактов в CI.
- `companion/` — исходники локального Windows-помощника и его тесты;
- `.github/workflows/companion.yml` — тест и проверка Windows-сборки без публикации artifact.

Публичный URL: `https://dovnaravwork.github.io/pc-check-links/`.

Страница не загружает внешние runtime-ресурсы, не содержит аналитики и ничего не отправляет. Внешние ссылки используются только как явные переходы на сайты разработчиков инструментов. Данные мастера хранятся в `localStorage` текущего браузера и удаляются кнопкой «Сбросить всё» после подтверждения.

Windows-помощник пока не связан кнопкой загрузки с публичной страницей. Его границы, команды проверки и обязательные условия перед выпуском описаны в [`companion/README.md`](companion/README.md).

Кнопка «Подготовить и открыть проверку» копирует проверяемую PowerShell-команду: она подтверждает Store-пакет Microsoft App Installer, точный alias и источник WinGet, устанавливает CPU-Z, GPU-Z, CrystalDiskInfo, HWiNFO и OCCT Personal, связывает EXE с разрешёнными путями, проверяет точных Authenticode-издателей и версии, собирает baseline/post события и состояние накопителей, а затем открывает инструменты. Бесплатный сценарий не управляет GUI OCCT и всегда оставляет итог `INCOMPLETE`, пока человек не подтвердит ручные нагрузочные этапы на сайте.

Внутренний SafeMode используется только для проверки подготовительного конвейера на контрольном Windows-ПК без запуска интерфейсов и нагрузки. Покупателю доступны On-site Screen примерно на 25–30 минут, домашний протокол примерно на 90–120 минут и отдельный Maximum-протокол на 8–12+ часов. Последний требует ручного UEFI-запуска MemTest86; полностью автоматический OCCT-сценарий возможен только с пользовательской Enterprise-лицензией. Итоговый мастер оценивает On-site Screen; статус `Пройдено` или `Торг` без заполненной заметки считается `Не проверено`.

## Происхождение диагностических файлов

Бинарники не входят в репозиторий и не раздаются GitHub Pages. На странице зафиксированы проверяемые UAC-издатели CPU-Z (`CPUID`) и HWiNFO (`REALiX, s.r.o.`); неизвестный издатель означает отмену запуска. Для каждой подготовленной флешки пользователь сохраняет manifest с точным именем файла, версией, SHA-256, датой и официальным URL. Значения хэшей не хардкодятся в сайт без подтверждённого файла конкретной версии — это защищает от устаревшего «правильного» хэша после обновления автора.

## Локальная проверка

```sh
node --test tests/site.test.mjs
python3 -m http.server 4174 --bind 127.0.0.1
```

Открыть `http://127.0.0.1:4174/`, проверить desktop/mobile, выбор всех четырёх статусов, восстановление после перезагрузки, сброс, копирование отчёта и «Печать / PDF».

## Выпуск

1. Обновить только файлы в этой папке и сохранить официальное происхождение ссылок.
2. Выполнить `node --test tests/site.test.mjs`.
3. Проверить `git status --short`, `git diff --check` и просмотреть diff. Перед commit убедиться, что `script.js`, `tests/`, `.github/workflows/verify.yml` и README добавлены в индекс: публикация одного HTML оставит мастер без логики. В релизе не должно быть бинарников, CDN, аналитики или загрузки данных.
4. Зафиксировать все перечисленные файлы в этом репозитории и отправить его ветку публикации только после явного разрешения владельца. Не использовать `git commit -am` для первого выпуска новых файлов.
5. После GitHub Pages deployment открыть публичный URL в обычном и мобильном viewport, затем повторить smoke-check на целевом Windows без VPN.

## Проверка после публикации

- HTML, `style.css` и `script.js` отвечают HTTP 200;
- все внутренние якоря работают;
- vendor-ссылки явно показывают внешний источник;
- статусы переживают перезагрузку, а reset очищает их;
- итог соблюдает приоритет `СТОП → НЕ ПРОВЕРЕНО → ТОРГ → ПРОЙДЕНО`;
- копирование и печатный/PDF-отчёт содержат поля, статусы, заметки и итог;
- при отключённом JavaScript инструкция остаётся читаемой;
- CPU-Z fallback, HWiNFO UAC и OCCT Stop проверены по фактическому Windows-сценарию.

## Rollback

1. Найти последний подтверждённый commit в истории вложенного репозитория `github-pages`.
2. Создать обычный revert проблемного release commit — не переписывать опубликованную историю.
3. Снова выполнить тесты и отправить revert только после разрешения владельца.
4. Дождаться GitHub Pages и проверить публичный URL, HTTP 200 для трёх runtime-файлов и основной маршрут.

Откат публикации не удаляет данные из уже открытого браузера. При изменении несовместимой схемы localStorage нужно увеличить версию ключа в `script.js` или явно описать пользователю сброс.
